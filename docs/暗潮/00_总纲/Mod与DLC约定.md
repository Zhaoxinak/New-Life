# Mod / DLC 约定

> 目标：让《暗潮》后续能稳定接入扩展包，而不是靠人工记忆和临时约定拼接内容。  
> 相关：[`数据库架构.md`](数据库架构.md) · [`effect词汇表.md`](effect词汇表.md) · [`内容注册总则.md`](内容注册总则.md) · [`ID命名与后缀语义总表.md`](ID命名与后缀语义总表.md)

---

## 1. 核心原则

1. **内容可扩，引擎只做解释器。**
2. **扩展包只能改定义层与本地化层，不能直接改玩家存档结构。**
3. **所有新增或覆盖内容都必须进入注册表。**
4. **覆盖原版必须显式声明，禁止静默抢占原版 ID。**
5. **扩展优先走“追加 / 挂钩 / 变体”，最后才走整条覆盖。**

---

## 2. 扩展包能做什么

| 能做 | 说明 |
|---|---|
| 新增定义对象 | 可新增 `char / loc / org / act / event / dialog / clue / item / ending` 等内容 |
| 覆盖定义对象 | 允许覆盖原版对象，但必须声明 `overrides` |
| 新增对话变体 | 可为已有事件追加新的对白皮或入口变体 |
| 新增系统挂钩 | 可为既有路线 / 职级 / 清算窗登记新的接入点 |
| 新增本地化 | 可覆盖或追加 `loc_key` |
| 新增战役实例 | 允许做整包独立战役，但仍要遵守核心契约 |

| 不能做 | 原因 |
|---|---|
| 新造未登记的 `op` | 必须先扩 [`effect词汇表.md`](effect词汇表.md) |
| 直接改 `run_*` schema | 存档兼容必须走迁移方案 |
| 复用原版主键换指向 | 会破坏引用关系和覆盖判定 |
| 跳过注册表直接落文档 | 后续无法校验依赖、覆盖、入口 |
| 直接把历史总源当权威入口 | 以拆分树和注册表为准 |

## 3. 包结构

建议结构：

```text
packs/<pack_id>/
  modinfo.yaml
  registry/
  def/
  dialog/
  loc/
  docs/
```

其中：

- `modinfo.yaml`：内容包元信息
- `registry/`：本包声明的事件、对话、覆盖、挂钩
- `def/`：结构化定义导出或未来机器表
- `dialog/`：本包提供的对白节点
- `loc/`：本包文案
- `docs/`：设计文档与策划说明

当前文档树仍以 `docs/暗潮/` 为主，但所有未来扩展都应能映射到上面的包结构。

---

## 4. `modinfo.yaml` 最低字段

```yaml
id: base
name: 暗潮本体
version: 1.0.0
type: campaign
depends: []
load_order: 0
provides:
  - campaign_anchao
  - route_endure
  - route_defect
  - route_foreign
overrides: []
```

字段说明：

| 字段 | 说明 |
|---|---|
| `id` | 包唯一标识，后续简称 `pack_id` |
| `type` | `campaign` / `dlc` / `mod` / `system` |
| `depends` | 依赖的包 |
| `load_order` | 数字越大越后覆盖 |
| `provides` | 本包引入的战役、路线、系统能力 |
| `overrides` | 覆盖的原版对象或入口槽位 |

## 5. 命名空间与 ID 纪律

### 原版

- 原版继续使用既有 ID，例如 `E020`、`char_lin_ruisheng`、`dialog_e020_start`。
- 原版 ID 与字段命名，以 [`旗标与命名.md`](旗标与命名.md) 为准。

### 扩展包

- 每个扩展包必须先声明 `pack_id`。
- 每个新增对象必须能追溯到 `pack_id`。
- 文档中允许沿用原版风格，但注册表必须补 `pack_id` 与覆盖关系。

### 覆盖纪律

- **禁止**直接把扩展内容写成原版 ID 并假装是原版。
- 若要覆盖原版 `E020`，必须在包级或条目级显式声明：

```yaml
overrides:
  - E020
```

- 若只是挂新对白皮，不应覆盖整个事件，而应登记成该事件的 `dialog variant`。

---

## 6. 注册表要求

扩展包新增或覆盖内容时，至少要同步以下入口：

- `事件注册表`
- `对话注册表`
- `内容包注册表`
- 必要时更新 `路线与系统挂钩表`

原则：

1. **事件存在** 不等于 **事件可被系统找到**；没注册就视为不存在。  
2. **对话存在** 不等于 **对白会被调用**；没注册就不会进入入口解析。  
3. **系统文档新增规则** 不等于 **运行上可接入**；需要登记挂钩点。  

---

## 7. 允许的扩展方式

### A. 追加

新增人物、地点、事件、对话、线索、物品、结局。  
适合新支线、新章节、新角色包。

### B. 变体

为既有事件新增路线变体、对白变体、演出变体。  
适合 DLC 给原剧情加额外分支，而不覆写整条主链。

### C. 挂钩

在既有系统点位上登记新的进入条件、互斥关系、收束方式。  
适合新增“章二另一种升阶主爽”或“新清算窗口”。

### D. 覆盖

完全替换原版条目。  
只在前 3 种都不够时使用，并且要显式标注 `overrides`。

---

## 8. 系统层与战役层

未来包体要明确自己是在扩哪一层：

| 层 | 允许内容 |
|---|---|
| 核心契约层 | 极少动；必须全局审查 |
| 系统模块层 | 新增规则文档、系统挂钩、玩法变体 |
| 战役实例层 | 新事件、新对白、新角色、新线索、新日程 |

默认推荐：**绝大多数 DLC / MOD 都优先扩战役层和系统挂钩层，不改核心契约层。**

- [`../_archive/暗潮_游戏设定与剧本_V3.md`](../_archive/暗潮_游戏设定与剧本_V3.md) 保留为历史总源和迁移参考。

---

## 10. 首轮实施要求

在完整工具链落地前，至少先保证：

1. 原版内容使用稳定 ID  
2. 所有核心逻辑只用白名单 `effect`  
3. 新增内容补齐注册表  
4. 覆盖关系明确可追踪  
5. 事件、对话、系统挂钩三类扩展可区分
